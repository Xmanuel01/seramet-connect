# Sales Through Finance: Corrections and Acceptance

## Release Boundary

These corrections are prepared for delivery through existing PR #138 on `codex/pilot-staff-integration` from `seramet-pilot-completion`. They are not installed on the live restaurant computer. No merge, deployment, protected database change, credential provisioning or migration was performed. Earlier local corrections were preserved. Pushing the branch does not certify deployment or live operation; GitHub CI results must be checked separately for the pushed commit.

## Validation

- Pre-push focused regression pass: **129 tests passed across 14 files** in one run, covering guest/QR, navigation, refund eligibility, rider registration/workload, cookbook scaling, inventory/procurement, requisition export, CRM, workforce rendering, attendance API and payroll. This is a targeted pass, not comprehensive release certification.
- Follow-up QR hardening: a configured active QR order channel is checked before rotating a capability or creating guest-session side effects. A new regression verifies missing channels leave existing capabilities, sessions and QR events unchanged.
- Requisition export is implemented for the currently loaded, authorized branch rows. CSV includes actual request identities, quantities and units, quotes delimiters correctly and neutralizes spreadsheet-formula text. Its scope is not an unbounded export of the complete historical database.
- 62 focused guest/QR, refund, rider and cookbook tests passed.
- 54 inventory/procurement, CRM, workforce rendering, attendance API, payroll and navigation tests passed. Inventory and CRM query regressions include disposable PGlite PostgreSQL execution through the production adapter, as well as SQLite. PGlite is not certification against a hosted PostgreSQL 16 server or live staging.
- TypeScript passed. ESLint over changed/new source and tests passed with zero errors and seven existing warnings (React refresh exports and hook dependencies); none were suppressed.
- Browser acceptance is recorded separately in `.seramet/category-acceptance/routes.json` and Playwright results. A rendering smoke check must not be called complete execution of every business action.
- The scan visited **67 routes** through Finance with **zero page exceptions, crash screens or API 5xx responses**. This successful scan preceded the final localized QR-channel and requisition-export changes; those changes received their own focused browser checks, not a repeated 67-route scan.
- Eleven distinct browser cases eventually passed across focused runs: four invoice/refund/rider/navigation cases, the route scan, QR issuance/session/revocation, inventory category/location/item creation, cookbook scaling, CSV download and two Front of House cases. This is not a claim that one aggregate run passed all eleven cases: the first ten-case run had seven passes and three test setup/locator failures. Inventory and cookbook passed after correcting dropdown selection; QR then exposed missing disposable channel configuration, which was supplied and guarded before its successful rerun. CSV was separately verified using a newly registered branch inventory item rather than assuming an unlocated recipe ingredient appears in the branch stock list.
- A final 33-test QR/export/workforce subset passed, including seven CSV tests and the new missing-channel regression; it overlaps earlier test counts and must not be added as 33 entirely new tests.
- The optional browser seed requires `CI=true`, `SERAMET_E2E=true`, an existing disposable pilot tenant, authorized branch membership and the required permissions. Its database path is the existing local `.seramet/development.sqlite`, not a staging connection.

## Remaining Blockers and Limitations

Final local checks passed: production client/server build, TypeScript, scoped ESLint (zero errors; existing warnings retained), formatting, production bundle secret/demo-identifier audit and `git diff --check`. CI was not dispatched. No single full release-certification run or live operational certification is claimed.

1. **Deployment:** the live application will continue showing its old behavior until these changes are reviewed and deployed through the approved release process. No deployment was authorized or performed in this task.
2. **Spreadsheet imports:** no inventory spreadsheet commit pipeline was newly implemented or enabled. Menu/historical file ingestion remains fail-closed. Genuine authenticated scanner evidence and domain-specific validation/approval are required; an unrestricted Excel picker is not a safe replacement.
3. **Campaign email:** no healthy production email adapter is registered. Configuration/provider implementation and non-production certification are still needed. The UI correctly refuses to create a sendable email campaign; no fake delivery or secret was added.
4. **Attendance:** the reported page crash did not reproduce in disposable render/API tests. Exact failing route, selected scope and sanitized browser exception from the deployed version are still required if it persists. Local smoke coverage is not evidence of live location/PIN authorization or real phone behavior.
5. **Operational prerequisites:** units, branch warehouses, stock, approved purchase orders, posting accounts and separate authorization remain necessary where the workflow requires them. Buttons are not unconditionally enabled to conceal a failed loader or missing authorization.
6. **Refund payout:** the receipt-linked approval register and payment-orchestrator payout lifecycle remain separate existing models. A recorded approval/rejection is not a cash/provider refund settlement certification.
7. **Hardware/providers:** no physical printer, real scanner, real campaign email or live payment-provider delivery was certified.

See `src/inventory/INVENTORY_PROCUREMENT_CORRECTIONS.md` for individual inventory controls, SQL reproductions and retained prerequisites. Daily Sales Journal and Payment Control were not changed during this pass. No further accounting redesign was started.
