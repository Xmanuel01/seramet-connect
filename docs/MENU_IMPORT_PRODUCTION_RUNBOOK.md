# Production Menu Import

## Architecture

The production path is:

`Menu Import UI -> authenticated setup API -> file security -> OnboardingService preview -> setup_imports/setup_import_rows -> explicit commit -> menu_catalog_items/menu_item_branch_settings -> verification -> operational catalogue -> POS/KDS/marketplace reader`

The browser holds only the selected file and preview presentation. The server derives the tenant from the authenticated actor, calculates the file digest and preview fingerprint, validates branch authority, and owns every authoritative write.

## Canonical Template

Template version 2 is generated by `createCanonicalMenuTemplate`. It is the only template downloaded by the dedicated Menu Import route and by the legacy export helper.

| Column                    | Meaning                                      | Validation or storage                                           |
| ------------------------- | -------------------------------------------- | --------------------------------------------------------------- |
| `templateVersion`         | Import contract version                      | Required in generated templates; future versions are rejected   |
| `itemCode`                | Stable tenant item identity                  | Required and unique per tenant                                  |
| `name`                    | Menu display name                            | Required                                                        |
| `categoryCode`            | Category identity                            | Required; retained as the authoritative category code           |
| `menuSection`             | Optional menu section                        | Validated text in item payload                                  |
| `description`             | Item description                             | Item column                                                     |
| `basePrice`               | Tenant base selling price in major units     | Converted through the central currency money rules              |
| `currency`                | ISO currency code                            | Must be globally known and active for the tenant                |
| `taxCode`                 | Active tax rule                              | Resolved by tenant and applicable branch                        |
| `serviceChargeApplicable` | Service-charge eligibility                   | Boolean item column                                             |
| `unitOfMeasure`           | Configured UOM code                          | Must resolve when populated                                     |
| `stationCode`             | Branch production station                    | Exact ID, normalized code, or explicit alias only               |
| `kitchenPrinterGroup`     | Routing hint                                 | Retained for review; warned until a printer-group master exists |
| `recipeCode`              | Existing recipe reference                    | Resolved to an active recipe ID or marked pending               |
| `modifierGroupCode`       | Modifier group reference                     | Retained with a warning until a modifier-group master exists    |
| `barcode`                 | External scan identity                       | Conflicts with another item are blocked                         |
| `sku`                     | Stock/menu identity                          | Conflicts with another item are blocked                         |
| `sellable`                | Tenant-level sellability                     | Boolean item column                                             |
| `branchCode`              | Row target for `ROW_BRANCHES`                | Must resolve to an assigned, active branch                      |
| `branchPrice`             | Branch override in major units               | Branch setting in integer minor units                           |
| `available`               | Branch ordering availability                 | Branch setting                                                  |
| `channels`                | Pipe/comma/semicolon-separated channel codes | Every code must resolve                                         |
| `prepMinutes`             | Preparation duration                         | Non-negative integer in item payload                            |
| `parLevel`                | Menu PAR hint                                | Non-negative integer in item payload                            |
| `imageFilename`           | Asset filename/reference                     | Retained with a warning until asset upload verifies it          |

Headers are case-insensitive and punctuation-insensitive. Known short/rich legacy aliases are mapped. A populated unknown column is reported and is never silently treated as canonical data.

CSV and Excel `.xlsx` files use the same canonical columns and authoritative preview/commit path. Excel workbooks are signature checked, limited to 10 sheets and 500 archive entries, and capped at 50 MiB expanded content. The importer reads the first worksheet, so the canonical menu must be on that sheet.

## Targeting Modes

- `TENANT_MASTER` creates or updates the tenant item only. It does not expose the item to any branch.
- `SELECTED_BRANCHES` writes explicit settings for each selected assigned branch.
- `ROW_BRANCHES` resolves each row's `branchCode` to an immutable branch ID.

All-branch read visibility does not grant mutation authority. The actor must be assigned to every target branch and must have branch-switch authority when targeting a branch other than the active branch. Commit checks the authority again.

POS and marketplace catalogue queries use an inner branch-activation join. Missing activation or `available=false` keeps the item out of operational ordering.

## Station Mapping

Station resolution is branch scoped and never fuzzy:

1. Exact station ID.
2. Case-insensitive exact station code.
3. Explicit station mapping supplied during preview.
4. Previously confirmed tenant/branch alias.

An unknown source value blocks the affected rows. The UI can map one repeated source value to a configured station code and rerun preview. Successful mappings are stored as tenant-scoped, branch-scoped aliases. A station from another branch is rejected by preview and by database trigger.

## Duplicate Policies

The current repository contract stores `ERROR`, `CREATE`, `UPDATE`, and `SKIP`:

- `ERROR`: reject existing stable codes.
- `CREATE`: create-only; existing codes are preview errors.
- `UPDATE`: update-existing-only; missing codes are preview errors.
- `SKIP`: existing codes become `SKIP` rows.

Preview rows show `CREATE`, `UPDATE`, `SKIP`, `NO_CHANGE`, or `ERROR`. Changing strategy, targets, or station mapping invalidates the browser preview and produces a different server fingerprint.

## Preview And Commit

The preview fingerprint contains tenant ID, SHA-256 file digest, template/importer version, normalized column map, duplicate policy, target mode, sorted target branch IDs, and reference mappings. Filename and browser timestamps are not authoritative identity.

Commit rejects expired previews and catalogue revisions that changed after preview. Synchronous writes use one database batch. On failure the batch rolls back and the import is marked `FAILED`. Imports over 500 rows enter the durable worker as `COMMITTING`; the client reports `QUEUED` and does not claim success.

After writes, verification counts created/updated/skipped records, verifies every expected tenant item and branch setting, and persists the summary. Only a verified result becomes `COMMITTED`.

## Price Rules

CSV prices are major-unit text. Seramet removes display separators and uses the central money abstraction for the currency's minor-unit precision. Persisted values remain safe integers. The UI formats the minor-unit value back as currency; it never labels `350.00` as `35,000 minor`.

Negative, malformed, excessive-precision, unknown, and tenant-inactive currency values block commit. Zero-price items remain valid.

## Security Limits

- Authenticated setup permission and server-derived tenant.
- Assigned-branch checks at preview and commit.
- Tenant/user database rate limits for preview and commit.
- Safe filename, MIME, extension, signature, file-size and row limits.
- Maximum 10 XLSX sheets, 500 ZIP entries, 50 MiB expanded workbook data, 100 columns and 10,000 characters per cell.
- Optional malware scanner boundary remains supported.
- CSV template/report cells use formula-injection escaping.
- Uploaded files and secrets are not logged.

## Manager Procedure

1. Configure branches and assign the importing manager.
2. Configure production stations for each target branch.
3. Download template v2 from Menu Import.
4. Enter immutable item, branch, station, tax and channel codes.
5. Select tenant-master, selected-branch, or row-branch targeting.
6. Select the duplicate policy and upload the file.
7. Map repeated unknown station values and rerun preview.
8. Resolve every blocking row and review create/update/skip effects.
9. Commit and wait for `COMMITTED` plus `catalogueVerified=true`.
10. Open the target branch POS and test KOT/BOT routing before service.

## Recovery

- `VALIDATED`: safe to commit while unexpired and current.
- `COMMITTING`: queued or being processed; do not re-upload as success.
- `COMMITTED`: persistence and catalogue verification succeeded.
- `REJECTED`: preview has blocking rows.
- `FAILED`: commit or verification failed; inspect the row/report and worker health.

If the catalogue endpoint fails, the UI preserves the last successful catalogue and shows a resource error. It does not render a false empty state. Provider, device, diagnostics, or opening-stock failures no longer clear menu data.

## Known Boundaries

- Category is currently an authoritative code on the menu item; there is no separate category-master table to validate against.
- Recipe IDs are verifiable, but an unmatched recipe code remains pending and does not create a recipe.
- Modifier groups and printer groups have no authoritative master in the current schema; populated references are retained and explicitly warned, not claimed as verified.
- Image filenames are retained but require the separate asset upload/mapping workflow for verification.
- The persisted duplicate-policy enum does not yet include a distinct `UPSERT` value. The supported production policies are documented above.
- Large imports are durable and verified, but they are not promoted from a separate staging catalogue in one final database swap. The UI therefore keeps them non-committed until worker verification finishes.

## Optional Previous POS Sales

The Menu Import page also exposes a separate one-time migration for sales exported from a previous POS. It accepts CSV or Excel `.xlsx`, requires a server preview and explicit commit, resolves branch codes, validates tenant currency, and blocks dates that already contain Seramet orders or invoices.

Historical sales are immutable archival facts. They contribute to historical sales trends but never replay live orders, KDS/KOT tickets, inventory consumption, payment collection, receipts, or journals. Reports mark them `HISTORICAL_SALES_WITHOUT_OPERATIONAL_DETAIL` because operational detail and COGS cannot be inferred from sales totals.

The migration is optional. `Skip for now` creates an audit event without preventing a later migration. After one migration is committed, database uniqueness prevents a second committed migration for the tenant. See `docs/PREVIOUS_POS_SALES_MIGRATION.md` for the contract and operator steps.
